## 0. 요약 — 사용자가 가장 크게 막히는 곳

- **검색이 의도대로 안 먹음**(파라미터 충돌·이름 불일치) — 파일 찾기부터 막힌다.
- **여러 파일을 한 번에 못 받음** — 체크박스로 고를 순 있는데 실행 버튼이 없다(주석처리).
- **"취소" 버튼이 死버튼** — 눌러도 되돌려지지 않고 무조건 성공 안내만.
- **완료 실패해도 "완료됐다"고 뜸** — 에러를 삼켜 성공으로 오인.
- **기계관리 화면은 통째로 가짜(목업)** — 실데이터·동작 전무. *(단, 이 화면은 사용자 작업 중인 미완성 파일 — 아래 O-5)*
- **소켓 포트 표기 모순**(8080 vs 30090) — 환경에 따라 실시간이 통째로 안 붙을 위험.
- **상태 라벨이 화면마다 3개** — "처리중" 필터 걸면 표엔 "다운로드완료". 상태를 신뢰 못 함.

### 라이브에서 확인된 정상 동작
- `cam/print` 렌더 정상, 헤더 "**실시간 연결됨**"(소켓 연결됨) ✓, 진행률 4카드 표시, 빈 상태 안내 "현재 출력 대기 중인 작업이 없습니다." ✓, 상단 버튼 "재로드/모니터링 중지/백업 초기화"(오타 아님).

## 0.5 라이브 실측 검증 (2026-07-01, 실데이터 기반)

> 화면이 빈 이유를 추적하다 **DB에 실데이터 존재**(`cam_file_receipts` 16건 / downloads 39 / checks 59, 전부 2025-08, status received·processing)를 확인. 백엔드 API를 직접 태워 아래를 **실측**했다(코드 추론이 아님).

| 검증 | 방법 | 결과 |
|---|---|---|
| **빈 목록 원인** | `GET /cam/data/receipts` (무필터) | **0건** — 백엔드가 기본 "오늘" 범위로 필터. 프론트 초기 로드(`+page.ts:22`)가 날짜 파라미터 없이 호출 → **파일 16건이 있어도 빈 목록**. |
| **동작 파라미터** | `?date=2025-08` vs `?startDate=..&endDate=..` | `date=2025-08` → **0건**, `startDate=2025-08-01&endDate=2025-08-31` → **16건**. `date`는 안 먹고 `startDate/endDate`만 유효. |
| **검색 필드(A1/A2)** | `?startDate..&filename=crown` / `&title=Zirconia` | `filename=crown` → 3건(파일명 필터), `title=Zirconia` → 2건(**카테고리/폴더 필터**), `filename=crown&title=abutment` → 0건(AND). → `filename`과 `title`은 **다른 필드**. 프론트 `filterPrintList`가 파일명 검색을 `title`(422)로 보내고 카테고리가 덮어씀(431) → **파일명 검색이 엉뚱한 필드로 가거나 소실**. `refreshFromDB`만 `filename`(558) 사용. |
| **단건 다운로드** | `GET /cam/data/download/single?id=84` | **404 "파일이 존재하지 않습니다"** — DB 기록은 있으나 실제 파일이 공유 마운트(`/mnt/winshare/DentalLab/...`)에 없어 실패. 에러 본문에 **서버 절대경로(debugPath) 노출**(정보유출). 이 환경에선 실제 파일 다운로드 불가. |

**즉 새로 확인된 막힘**: (A0) 초기 진입 시 파일이 있어도 빈 목록, (A8) 다운로드 404 + 경로 유출. A1/A2는 실데이터로 재확인됨.

### 임의 파일 주입 end-to-end 실측 (수신→목록→다운로드→완료)
> 이 환경엔 실파일이 없어(공유 미마운트) 다운로드가 404였으므로, **테스트 STL 파일 + 오늘 날짜 수신 레코드를 직접 심어** 전 과정을 태우고 **검증 후 원복**(receipts 16→17→16, 테스트 로그/파일 삭제)했다.

| 단계 | 실측 결과 |
|---|---|
| ① 수신→목록 | 오늘 날짜 레코드 삽입 즉시 목록에 표출(브라우저 UI에도 행 노출) → **A0가 순전히 "기본 날짜=오늘" 불일치임을 역으로 증명** |
| ② 다운로드 | `download/single?id` → **HTTP 200**, 실제 파일 스트리밍(Content-Disposition, 132B 그대로 수신) → 파일이 물리적으로 있으면 다운로드 정상. **부수효과: status `received`→`processing`(=다운로드완료)로 변경**(상태 라벨 의미역전 실증) |
| ③ 완료 | `POST complete {fileId}` → 토큰 있으면 `{"status":"ok"}`, DB status→`completed` ✓ |
| UI 확인 | 완료 후 브라우저 목록에 상태 "**가공완료**"(초록), 진행률 카드 긴급 100%·완료 100%(더미 아닌 실값) 표시 |

**추가로 실측 발견**:
- **🔴(보안) 인증 정책 불일치**: `receipts`(목록)·`download/single`(파일 다운로드)은 **토큰 없이도 200**으로 데이터/파일 반환. 반면 `complete`만 **401**(토큰 필요). → **미인증 사용자가 CAM 파일을 목록·다운로드 가능**(민감 파일 노출). 다운로드 404 응답의 `debugPath`(서버 절대경로)도 유출.
- **🟡 탭 카운트 오류(라이브)**: 목록에 1건이 떠 있는데 탭 배지는 "전체 0 / 다운로드 전 0 / 다운로드 완료 0 / 완료 0"로 **전부 0** → 탭 카운트가 실제 목록을 반영 못 함.
- **🟢 수신시간 날짜 없음(라이브 재확인)**: 표에 "오후 1:26:48"처럼 시각만.

## 수신 파이프라인 안정성 테스트 (2026-07-01, 실측)

> 이전 300건 테스트는 DB 직접 삽입이라 실제 수신 경로를 안 거쳤음. 이번엔 **실제 chokidar 파일 감시 → receipt 생성 → 소켓 → 프론트** 전체 파이프라인을 순차·랜덤 타이밍으로 검증.

**방법**: 소켓서버 감시폴더를 로컬(`test_folders/긴급·일반`)로 임시 지정 후 재시작 → 파일 **300개를 순차 투입**(랜덤 딜레이 0.05~0.25s, 총 45초, 긴급/일반 랜덤, 원자적 rename 쓰기).

**결과 (안정)**:
| 검증 | 결과 |
|---|---|
| 투입 300 → receipt 생성 | **정확히 300** (누락 0) |
| 중복 수신 | **0** (같은 파일 2회 없음) |
| 상태 | 전부 `received` |
| 폴더 분류 | 긴급 117 / 일반 183 (경로 기반 정상 분류) |
| 프론트 실시간 | 탭 300·진행률 300/300·리스트 최신순 정상 반영 |
| 에러 로그 | 수신 관련 에러 없음 |

→ **순차·랜덤 도착에서 수신 파이프라인은 누락·중복 없이 안정적**. (`awaitWriteFinish` 0.5s로 부분파일 방지, `ignoreInitial`로 기존파일 무시)

**🔴 중대 운영 리스크 (별도)**: 실제 감시 폴더(`.env` `FOLDER_URGENT=/Volumes/backup/DentalLab/cam/긴급`)가 **현재 마운트 안 됨** → 그 상태에선 워처가 존재하지 않는 경로를 감시해 **수신이 전혀 안 됨**. 파이프라인 로직은 안정적이나, **감시 대상 볼륨/폴더 부재 시 명확한 경보·헬스체크**가 필요(무음 실패 방지). 운영 안정성의 핵심.

### 감시 폴더 헬스체크/경보 구현 (2026-07-01)
> 위 리스크 대응. 감시 폴더 접근 불가를 감지해 프론트에 경보.

- **백엔드(소켓서버)**: `checkAndBroadcastFolderHealth`(시작 즉시 + 30초 주기) → `cam/monitor/health {healthy, inaccessible:['urgent'|'normal'], checkedAt}` 브로드캐스트(경로 미노출). 커밋 `13d6a4f`·`ed8c3c7`.
- **프론트**: `folderMonitorHealth` store + PrintView 상단 경보 배너("수신 폴더에 접근할 수 없습니다 … 새 파일 수신 중단 가능"). 커밋 `b0046d0`.
- **테스트 중 발견한 핵심 동작 2가지**:
  1. **자동 생성 + 로컬 폴백**: 설정 폴더가 없으면 백엔드가 `mkdir` 시도 → 실패 시 **로컬 `test_folders`로 조용히 폴백**하고 `FOLDER_PATHS`를 덮어씀. 즉 진짜 무음 실패는 "수신 자체 중단"이 아니라 **의도한 폴더 대신 엉뚱한 로컬 폴더로 재라우팅**(운영자 인지 불가). → 헬스체크가 폴백 후 경로를 보면 healthy로 오판하므로, **원래 설정 경로(`ORIGINAL_FOLDER_PATHS`)를 검사**하도록 수정(`ed8c3c7`). `/Volumes/backup`(미마운트) 설정 시 "접근 불가 감지: urgent" 로그로 검증됨.
  2. **소켓 인증 만료 데드엔드(C10)**: 긴 세션/서버 재시작 후 소켓이 "인증이 만료되었습니다"로 끊긴 채 복구 못 함 → 헬스 배너 시연도 이때 막힘. **아래 C10 수정으로 해결**.
> 현재 로컬 임시 수신 폴더(`.env` `FOLDER_URGENT/NORMAL=…/test_folders/긴급·일반`)로 수신 동작 확인(파일 투입 → receipt 생성). 실제 운영 배포 시 `.env`를 실 저장소 경로로 되돌릴 것.
