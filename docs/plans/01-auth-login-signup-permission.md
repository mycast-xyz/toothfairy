# 기획안 01 — 로그인 / 회원가입 / 회원 권한 개편

> 작성 2026-06-30 · 대상: 인증(로그인·회원가입) + RBAC 권한 체계
> 선행 분석: [`docs/status/01-auth-and-role.md`](../status/01-auth-and-role.md)
> 목적: **"CAM/센터 관리자에게 권한을 이임해도 계속 user로 보이는 버그"** 를 근본 해결하고, 로그인/회원가입/권한 흐름을 일관된 단일 체계로 정리한다.

---

## 1. 배경 / 문제

현재 인증·권한은 **두 개의 역할(role) 시스템이 분리**되어 동작이 깨져 있다.
- **(A) 권한용 문자열 enum**(`all_cam` 등): JWT 클레임에서만 옴 → 메뉴/페이지 권한을 좌우.
- **(B) 관리용 `roleId` 숫자**: 어드민의 "이임"이 바꾸는 값. enum과 **매핑 코드가 전무**.
- 결과: 어드민이 `roleId`를 바꿔도 당사자 **JWT가 재발급되지 않아** 계속 폴백 `user`.

부수 문제: `userInfo` 쿠키 `maxAge:30초` 버그, 메뉴-페이지 **권한표 불일치**(메뉴는 보이는데 진입 차단), 리프레시 엔드포인트/응답 불일치, httpOnly 토큰 평문 노출, 회원가입 폼에 **소속/역할 선택이 없음**(역할 부여가 전적으로 사후·수동).

---

## 2. 목표 / 비목표

**목표**
1. 역할 체계를 **고정 enum 단일 소스**로 통일한다.
2. 회원가입 → **희망 소속 선택** → 어드민 **승인 + 역할 확정** → **즉시 권한 반영**까지 끊김 없는 흐름.
3. 메뉴 노출과 페이지 진입 권한을 **하나의 권한표**로 일치시킨다.
4. 인증 관련 보안/품질 결함(토큰 로깅·평문 반환·쿠키 maxAge·하드코딩 URL) 정리.

**비목표 (이번 범위 아님)**
- 비밀번호 재설정(`/login/password`) 고도화 — 흐름 점검만, 별도 기획.
- 소셜/SSO 로그인, 2FA.
- 동적 커스텀 역할 생성 기능 — **결정①에 따라 폐기/단순화**(아래).
- **회사/거래처 단위 데이터 격리(멀티테넌시)** — **확정: 불필요.** 권한은 역할(enum)만으로 판단하며, 같은 역할은 동일 데이터 접근. (`role + corpId` 2축 설계는 하지 않음.)

## 3. 핵심 설계 결정 (확정됨)

| # | 결정 | 내용 |
|---|---|---|
| **①** | **고정 enum 통일** | 역할은 `all_admin / all_lab / all_center / all_cam / user` 5종으로 고정. 관리용 `roleId`/동적 `Role` 테이블은 **폐기 또는 enum 매핑**으로 단순화. 권한 로직이 이미 enum 기반이라 가장 깔끔. |
| **②** | **가입 최소정보 + 어드민이 역할 전적 부여** | 가입은 아이디/비번/이름만. **소속/역할 선택 없음.** 어드민이 승인 대기 목록에서 승인하며 역할(enum)을 부여한다. |
| **③** | **역할 변경 시 강제 재로그인으로 즉시 반영** | 어드민이 승인/이임하면 백엔드가 해당 유저 토큰을 **무효화** → 다음 요청에서 재로그인하며 새 역할 적용. |

> `'admin'` enum 값은 거의 미사용이므로 **`all_admin`으로 통합 후 제거** 권장(결정 필요 항목 §9-1).

## 4. 목표 역할 모델

### 4-1. 역할(권한 카테고리) — 고정 enum
| role | 의미 | 주요 접근 |
|---|---|---|
| `all_admin` | 전체 관리자 | 전 메뉴 + 설정/사용자관리 |
| `all_lab` | 기공소 | 의뢰서 등록/목록/배송 |
| `all_center` | 기공센터 | 출력물/청구서/거래처 |
| `all_cam` | CAM | 출력물 관리/기계관리/모니터링 |
| `user` | **미승인·기본값** | 대시보드/캘린더 + "승인 대기" 안내 |

### 4-2. 승인 상태와 역할 분리
- **`isPermitted`(boolean)** 와 **`role`(enum)** 은 별개 축.
  - 가입 직후: `role=user`, `isPermitted=false`. (소속/역할 선택 없음 — 어드민이 부여.)
  - 어드민 승인: `isPermitted=true` + `role=<부여한 enum>`.
- **진실의 단일 소스 = 백엔드.** 프론트는 **JWT `userRole` 클레임만** 신뢰한다. `roleId` 사용 중단.
- 백엔드는 토큰(로그인/리프레시) 발급 시 사용자의 확정 `role`을 **`userRole` 클레임(enum 문자열)** 으로 넣는다.

### 4-3. 이임(역할 변경) 즉시 반영 전략 — 버그의 핵심
- 어드민이 역할 변경 → 백엔드 저장 → **다음 토큰 발급 시 새 role 반영**.
- **확정 방식: 강제 재로그인.** 역할 변경 시 백엔드가 해당 유저의 access/refresh 토큰을 **무효화** → 다음 요청에서 401 → 로그인 페이지로 유도하며 새 역할이 적용된 토큰 재발급.
- 프론트: 401(토큰 무효) 응답 시 "권한이 변경되어 다시 로그인이 필요합니다" 안내 후 로그아웃 처리 → `/login`.

## 5. 사용자 스토리

- **가입자**로서 최소 정보(아이디/비번/이름)만으로 빠르게 가입하고, 관리자 승인을 기다리고 싶다.
- **미승인 사용자**로서 로그인하면 "승인 대기 중"임을 명확히 안내받고, 승인 전엔 차단된 메뉴가 보이지 않길 원한다.
- **어드민**으로서 **승인 대기 목록**에서 가입자를 보고, **승인하며 역할을 부여**하고 싶다.
- **권한을 이임받은 관리자**로서, 어드민 승인 후 **(안내에 따라 한 번 재로그인하면) 즉시** 해당 권한 메뉴가 보이길 원한다.
- 모든 사용자로서, **메뉴에 보이는 항목은 클릭 시 반드시 진입 가능**해야 한다(보이는데 차단되는 모순 제거).

## 6. 화면 / 플로우

### 6-1. 회원가입 (`/login/create`)
- 폼은 **현행 유지(아이디/비번/비번확인/이름)** — 소속/역할 선택 없음.
- 제출: `POST /api/v0/account/create/account` `{ id, password, name }` (passwordChk는 전송 제외). 백엔드는 `role=user, isPermitted=false`로 생성.
- 가입 성공 → "가입 완료, 관리자 승인 후 이용 가능" 안내 → `/login`.
- **수정할 잔버그**: 아이디 중복검사 **디바운스**(현재 키입력마다 호출), label `for`/input `id` 정합(`for="email"`→`name`), 변수명 정리(`emailError`→`idError`), 하드코딩 URL → ConfigService, `passwordChk` 전송 제외.

### 6-2. 로그인 (`/login`)
- 기존 흐름 유지(`POST /api/v0/account/login` → 쿠키 발급). 단:
  - 하드코딩 `BACKEND_API_URL` → ConfigService.
  - JWT 전체 페이로드 **콘솔 로깅 제거**.
  - `userInfo` 쿠키 **`maxAge` 버그 수정**(30초 → 의도값).
- 로그인 후 `isPermitted=false`면 **승인 대기 화면/배너**로 유도(차단 메뉴 숨김).

### 6-3. 어드민 승인 + 역할 부여 (`/setting/user`)
- **승인 대기 탭** 신설: `isPermitted=false` 사용자 목록(아이디/이름/가입일).
- 승인 모달: 역할 enum 선택(드롭다운: all_lab/all_center/all_cam/all_admin) → 승인.
  - 호출: `PATCH /api/v0/setting/users/:id/role` `{ role: <enum>, isPermitted: true }` (현 `roleId` → **`role` enum** 으로 계약 변경).
  - 승인/역할 변경 시 백엔드가 **해당 유저 토큰 무효화**(§4-3).
- 기존 `EditUserRoleModal`을 enum 기반으로 개편(`roleId`/`Role` 의존 제거).

### 6-4. 권한 enforcement (서버 게이트)
- `hooks.server.ts`가 단일 게이트로 유지. **권한표를 단일 소스로 통합**.
- 미승인(`isPermitted=false`)은 화이트리스트 경로(대시보드/캘린더/승인대기)만 허용.

## 7. 데이터 & API 요구사항

### 7-1. 백엔드 계약 (★필수★ — 프론트 단독 불가)
> **확정: 백엔드(REST 서버)는 직접 수정 가능.** 따라서 프론트 우회책(임시 roleId→enum 매핑 테이블)은 쓰지 않고, 아래 계약을 백엔드에 반영하는 **정공법으로 진행**한다.
1. **JWT `userRole` 클레임 = 확정 role enum**. 로그인·리프레시 모두 동일하게 포함.
2. **회원가입은 최소정보**(`id/password/name`)만 수용. 가입 시 `role=user, isPermitted=false`.
3. **역할 변경 API 계약 변경**: `PATCH /setting/users/:id/role` 가 **`role`(enum 문자열)** + `isPermitted`를 받도록(현 `roleId` 숫자 대체). **변경 시 해당 유저 토큰 무효화**(§4-3 강제 재로그인).
4. **리프레시 경로/응답 통일**: `/account/refresh` vs `/auth/refresh`, `{success,token}` vs `{accessToken,refreshToken}` 중 하나로 확정.
5. 승인 대기 목록 조회(필터 `isPermitted=false`) 지원.

### 7-2. 프론트 (단독 가능)
- `ConfigService` 엔드포인트 정리: `auth.{login,refresh,validateId,createAccount}` 추가, 하드코딩 제거.
- 권한표 단일화: `MENU_PERMISSIONS`(`UserRole.ts`)를 단일 소스로, `PermissionService.canAccessPage`가 이를 참조. `pagePermissions` 제거. 누락 경로(`/lab/*`,`/cam/*`,`/center/*`,`/setting/*`,`/calender`,`/main`) 보강, 표기 통일.
- `roleId`/이중 `User` 모델 제거 → `model/user/UserRole.ts`의 `User` 단일화.
- 보안/품질: JWT 콘솔 로깅 제거, `/api/auth/token` 평문 반환 제거(또는 비-민감 정보만), localStorage 토큰 의존 정리, `userInfo` maxAge 수정, 중복 디코딩(hooks/+layout.server/login) 공용 함수화.

## 8. 수용 기준 (AC)

- [ ] 가입은 아이디/비번/이름만으로 완료되고, 백엔드에 `role=user, isPermitted=false`로 생성된다.
- [ ] 미승인 사용자는 로그인 후 "승인 대기" 상태가 명확히 보이고, 권한 메뉴가 노출되지 않는다.
- [ ] 어드민이 승인+역할 부여 시 해당 유저 토큰이 무효화되고, **재로그인 1회 후** 맞는 메뉴/페이지에 접근 가능하다. **더 이상 `user`로 고정되지 않는다.**
- [ ] 메뉴에 보이는 모든 항목은 클릭 시 진입 가능하다(보이는데 차단 0건).
- [ ] JWT 전체 페이로드가 콘솔/로그에 남지 않는다.
- [ ] `userInfo` 쿠키가 의도한 시간 동안 유지된다(30초 버그 해소).
- [ ] 프론트 어디에도 백엔드 URL/엔드포인트 하드코딩이 없다(인증 범위 내).
- [ ] `roleId` 기반 코드가 제거되고 역할은 enum 단일 경로로만 흐른다.

## 10. 작업 분해 (구현 단계)

### Phase 0 — 사실 확인
- 이임된 계정으로 로그인 → JWT `userRole/role` 클레임 실측(원인 A/B 확정).
- 백엔드 팀과 §7-1 계약 합의.

### Phase 1 — 프론트 권한 기반 정리 (백엔드 독립)
- 권한표 단일화(`UserRole.ts`/`PermissionService`), 누락 경로 보강.
- `roleId`/이중 `User` 모델 제거, enum 단일화.
- `userInfo` maxAge·JWT 로깅·하드코딩 URL·중복 디코딩 정리.

### Phase 2 — 회원가입 잔버그 정리 (백엔드 독립)
- 아이디 중복검사 디바운스, label/for 정합, 변수명 정리, 하드코딩 URL → ConfigService, `passwordChk` 전송 제외.
- (폼 구조 변경 없음 — 소속 선택 추가 안 함.)

### Phase 3 — 어드민 승인/역할 부여 (백엔드 계약 후)
- 승인 대기 탭 + 승인 모달(enum 기반) 개편, `PATCH .../role` 계약을 `roleId`→`role` enum + `isPermitted`로 전환.

### Phase 4 — 강제 재로그인(토큰 무효화) 연동 + 검증
- 백엔드 토큰 무효화에 맞춰 프론트 401 처리: "권한 변경, 재로그인 필요" 안내 → 로그아웃 → `/login`.
- 미승인 사용자 "승인 대기" 화면/메뉴 숨김 처리.
- QA: 5개 역할 × 승인 전/후 메뉴·페이지 접근 매트릭스 검증.
