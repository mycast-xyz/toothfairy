# 기획안 07 — 화면 박스 크기(디자인 밀도) 정리 방안

> 작성 2026-07-01 · 상태: **QA + 방안(Phase 1 착수)**
> 배경: "화면의 박스(카드·컨테이너·섹션)들이 전반적으로 너무 커서 한 화면에 정보가 적게 들어간다"는 사용자 지적.
> 방법: 라이브 브라우저 QA + 코드 크기·여백 패턴 조사(tailwind 유틸리티 사용처 grep).

---

## 0. 문제 요약

- 박스가 커 보이는 것은 **특정 페이지의 문제가 아니라 앱 전반의 밀도(density) 설정**이 낮기 때문.
- **`tailwind.config.ts`는 순정**(`theme.extend` 비어있음) → 모든 크기가 각 컴포넌트 유틸리티 클래스에 하드코딩. 전역 축소는 (a) 공통 컴포넌트로 뽑거나 (b) config에 배율 주입 필요.
- 라이브 확인(의뢰 목록): 카드마다 상태 배지가 **카드 전체 높이를 채우는 큰 블록**(`w-60 p-8 px-12 text-xl`), 환자명·금액이 `text-2xl`, 페이지 외곽 `p-8 mt-8` → 한 화면에 2~3건만 보임.

## 2. 전략 — "안전한 표준화 우선, 위험한 전역 override 지양"

두 갈래 중 **컴포넌트/공통화 기반**을 권장한다.

- **권장: 공통 컴포넌트·단일 지점 축소** — PageHeaderBar(단일 파일), 공통 `<main>` 래퍼, 개별 페이지 국소 축소. 영향 범위가 명확하고 되돌리기 쉬움.
- **비권장(신중): `tailwind.config`의 spacing 배율 재정의**(예 `spacing.8: 24px`) — `p-8`/`mt-8`/`w-8`/`gap-8` 등 **모든 `-8` 유틸리티**에 동시 영향 → 패딩뿐 아니라 width/height/gap까지 축소돼 예측 못 한 깨짐. 밀도 조정에는 과한 도구.

### 한 번에 바꾸면 위험 → 파일별 확인 필요
- `py-3.5`/`py-4` **165곳 일괄 치환**(테이블·버튼·배지 혼재 → grep replace 오작동).
- `ml-64`/`w-64` **한쪽만** 변경(사이드바·본문 이원화 → 레이아웃 깨짐, 반드시 쌍으로).
- `text-2xl`(44곳)/`text-lg`(73곳) **전역 축소**(금액·강조 숫자 포함 → 가독성 손상).

## 3. 단계별 방안

### Phase 1 — 헤더 컴팩트화 (✅ 착수: `PageHeaderBar` 1파일 → 16페이지)
`PageHeaderBar.svelte`: `py-6`→`py-3`, `text-3xl`→`text-2xl`. **위험 최소·즉효**. (적용 완료)

### Phase 2 — 공통 페이지 컨테이너 도입
동일한 `<main class="ml-64 mt-8 … p-8">` 14곳을 공통 `PageContainer.svelte`(또는 `+layout.svelte` 래퍼)로 뽑고 외곽 여백을 한 곳에서 제어(`p-8`→`p-6`, `mt-8`→`mt-4`). 이후 사이드바 폭(`w-64`↔`ml-64`)도 이 컨테이너에서 함께 조정 가능(원인 1·7 동시 해결). `routes/+layout.svelte`가 이미 데스크톱/모바일 분기를 가져 삽입 지점으로 적합.

### Phase 3 — 선별 축소(국소, 안전한 것부터)
- 의뢰목록 카드 상태 버튼(원인 3): `p-8 px-12 text-xl`→`px-4 py-2 text-sm`, 환자명/금액 `text-2xl`→`text-lg`. **국소·즉효**.
- 청구서 화면(원인 5): `sm:p-10`→`sm:p-6`, `text-4xl`→`text-2xl`(PDF 뷰와 분리 확인).
- 검색 입력(원인 6): `h-12`+`py-4` 중복 제거(`h-10`).

### Phase 4 — 테이블 밀도 표준화(신중)
공통 테이블 셀 클래스/컴포넌트가 없어 일괄 치환 위험 → **페이지별로** 셀 `py-3.5`→`py-2.5`, `py-4`→`py-2` 적용(company/center/print/invoice 순). 또는 공통 `.table-cell` 유틸을 `app.css`에 정의해 점진 이관.

---

## 4. 결정 필요

- **O-1. 밀도 강도** — "약간 컴팩트"(p-8→p-6, py-6→py-3) vs "많이 컴팩트"(p-8→p-4). 우선 Phase 1(약간)으로 체감 확인 후 조정 권장.
- **O-2. 접근 방식** — 공통 컴포넌트(권장) vs tailwind config 배율(비권장). 본 방안은 컴포넌트 기반 전제.
- **O-3. 사이드바 폭** — `w-64` 유지 vs `w-56`으로 축소(가로 공간 확보, Phase 2에서 컨테이너와 함께).

> 진행: Phase 1 적용 완료. 나머지는 O-1(강도)·O-2(방식) 확정 후 Phase 2→3→4 순으로 국소·검증 진행. 각 단계는 라이브 스크린샷 before/after로 확인.
